## 二、背景与目标

### 2.1 背景

Windows 对传统 Win32 应用提供了成熟的快捷方式创建路径（右键 exe → 发送到桌面）。但 **UWP / Microsoft Store 应用（MSIX 包）没有可直接访问的 exe 路径**：安装目录 `WindowsApps` 受系统 ACL 保护，用户在资源管理器里根本无法进入。

系统提供的唯一官方路径是一个隐藏的虚拟文件夹，需要用户手动完成 **5 步操作**：

1. `Win + R` 打开「运行」对话框
2. 输入 `shell:AppsFolder` 并回车
3. 在混杂了全部已安装应用的列表中肉眼查找目标应用
4. 右键 → 「创建快捷方式」
5. 系统弹出 **「Windows 无法在此位置创建快捷方式。要在桌面上创建快捷方式吗？」** → 点击「是」

**核心矛盾**

| 问题 | 具体表现 |
| --- | --- |
| 入口不可发现 | `shell:AppsFolder` 是一个隐藏命令，不在任何菜单里，只能靠搜索/口口相传 |
| 列表不可检索 | 虚拟文件夹内条目混杂（本机实测 212 项），无排序、无分类，找应用靠肉眼滚动 |
| 弹窗制造困惑 | 「无法在此位置创建」是系统对虚拟文件夹的必然提示，但用户第一反应是"我做错了？会搞坏系统？" |
| 无法批量 | 一次只能右键一个应用，重装系统后要重复 N 遍 |
| 无脚本能力 | 企业部署、批量初始化场景完全无法自动化 |

**市场验证**

- 搜索 `shell:AppsFolder` 可得到大量教程内容（MakeUseOf、AddictiveTips、ASKVG、NinjaOne 等均专门撰文），说明需求真实存在且长期未被工具化。
- 现有第三方方案中，仅 **TileIconifier** 部分覆盖（定位为开始菜单磁贴美化，2017 年后停更，Win11 兼容性存疑）。
- **结论：不存在专注此场景且活跃维护的工具** —— 这是一个「有明确教程需求、无对口产品」的空档。

### 2.2 目标

| 层级 | 目标 | 衡量方式 |
| --- | --- | --- |
| 产品目标 | 将 5 步手动流程压缩至 **3 步以内**（打开 → 搜索 → 点击） | 完成一次创建的操作步数 ≤ 3 |
| 用户目标 | 不懂 `shell:AppsFolder` 的用户也能零文档上手 | 首次使用成功率 ≥ 90% |
| 技术目标 | 产出的快捷方式与系统手动创建**完全同构** | 双击可启动；图标自动继承；`System.Link.TargetParsingPath` 等于 AUMID |
| 工程目标 | 零第三方依赖、免安装、单文件分发 | 仅依赖系统自带编译器；exe < 100 KB |

### 2.3 成功标准（v1.0 发布判定）

- [ ] 枚举结果与系统 Shell 计数 100% 一致（本机基准 212 项）
- [ ] UWP 与 Win32 两类应用均能成功创建、双击可启动
- [ ] CLI `--list` / `--create` 退出码与输出格式符合约定
- [ ] 中文界面与输出无乱码
- [ ] GUI 启动无崩溃、批量创建不卡界面

### 2.4 非目标（明确不做）

| 不做的事 | 原因 |
| --- | --- |
| ❌ 开始菜单磁贴美化、图标自定义绘制 | 与 TileIconifier 定位区分，避免功能发散 |
| ❌ 应用启动器 / 快捷启动面板 | 不与 PowerToys Run、Listary 竞争 |
| ❌ 跨平台（macOS / Linux） | 核心能力强依赖 Windows Shell 命名空间 |
| ❌ v1.0 联网、上传用户数据 | 桌面小工具，隐私优先，无服务端 |
| ❌ 自定义启动参数 / 快捷键 / 管理员标志 | 保持系统默认行为，减少兼容风险 |

## 三、故事介绍

### 3.1 名词解释

| 名词 | 全称 / 含义 | 在本产品中的作用 |
| --- | --- | --- |
| **UWP** | Universal Windows Platform，微软通用 Windows 平台应用 | 无 exe 路径，必须走 AUMID 方案创建 |
| **MSIX** | 现代 Windows 应用打包格式（UWP 的演进） | 与 UWP 同等处理，统一按 AUMID 创建 |
| **AUMID** | App User Model ID，如 `Microsoft.WindowsCalculator_8wekyb3d8bbwe!App` | UWP 应用的唯一标识，创建快捷方式的核心入参 |
| **shell:AppsFolder** | Shell 命名空间，对应「所有应用」虚拟文件夹 | 本产品的数据源，等价于开始菜单全部应用的枚举入口 |
| **.lnk** | Windows 快捷方式文件（Shell Link） | 最终交付物 |
| **PIDL** | Pointer to an Item ID List，Shell 命名空间中的项目标识链 | `SHParseDisplayName` 的解析产物，供 `SetIDList` 使用 |
| **IShellLinkW** | Shell 链接 COM 接口 | 写入快捷方式目标的核心接口 |
| **IPersistFile** | COM 持久化接口 | 将构造完成的快捷方式落盘为 `.lnk` |
| **SetIDList** | IShellLinkW 的方法：以 PIDL 直接指定目标 | UWP 快捷方式的**原生**实现方式（区别于 `SetPath` 指定 exe） |
| **Win32 应用** | 传统桌面程序，有独立 exe 文件 | 走 `SetPath` 路径创建 |

### 3.2 故事概述

**主角**：李明，普通 Windows 11 用户，刚重装完系统。

**场景**：他想把「计算器」和「截图工具」放到桌面——他习惯从桌面启动常用工具。右键开始菜单里的计算器，只有「固定到开始屏幕」和「固定到任务栏」；去 `C:\Program Files\WindowsApps` 找，文件夹被系统锁死。他搜了半天，才在一个技术论坛里看到有人提到 `shell:AppsFolder`。

**他照着教程操作**：`Win+R` → 输入 `shell:AppsFolder` → 在两百多个条目里翻找 → 右键 → 「创建快捷方式」→ 系统弹窗：「无法在此位置创建快捷方式，要在桌面上创建吗？」→ 他愣住了，不确定点「是」会不会搞坏什么 → 小心确认 → 图标终于出现。

**转折**：一周后他换了台电脑，又要在新机器上重复一整套流程。这次他想：「这明明是个很机械的操作，为什么没有个小工具？」

**产品介入**：他找到「桌面快捷方式生成器」，双击 exe → 搜索框输入「计算器」→ 双击结果 → 桌面上出现计算器图标。全程 3 秒、2 步操作，没有任何需要理解的系统概念。

**故事落点**：这个产品的价值不在"技术多难"，而在于**把一段需要查阅教程才能完成的隐藏系统流程，变成一个人人不看说明就会用的操作**。

### 3.3 价值分析

**用户价值**

| 价值点 | 说明 |
| --- | --- |
| 认知成本归零 | 用户无需了解 AUMID、`shell:AppsFolder`、PIDL 等任何概念 |
| 步骤压缩 | 5 步（含 1 次概念困惑 + 1 次风险判断）→ 2 步 |
| 批量能力 | 勾选多个应用一次创建，手动流程无法做到 |
| 可脚本化 | CLI 支持部署脚本 / 批处理集成，IT 场景可用 |
| 结果可靠 | 与系统手动创建产物同构，非"假快捷方式" |

**方案对比（技术差异化）**

| 方案 | 实现方式 | 图标 | 双击行为 | 原生度 |
| --- | --- | --- | --- | --- |
| **本产品** | `SHParseDisplayName` + `IShellLinkW.SetIDList` | ✅ 自动继承应用图标 | ✅ 原生启动 | 与系统产物同构 |
| 常见 PowerShell 脚本 | `TargetPath = explorer.exe` + `Arguments = shell:AppsFolder\AUMID` | ⚠️ 常显示 explorer 图标，需手动指定 | ⚠️ 经 explorer 中转 | 取巧 |
| `.appref-ms` 文件 | 生成 ClickOnce 引用文件 | ⚠️ 不稳定 | ⚠️ 部分场景失效 | 非标准 .lnk |
| URI 快捷方式（`ms-clock:`） | 创建 URL 快捷方式 | ⚠️ 通用图标 | ⚠️ 仅少数预装应用有 URI | 覆盖面窄 |
| 手动 `shell:AppsFolder` | 系统右键 | ✅ | ✅ | 基准线 |

**竞品格局**

| 竞品 | 类型 | 重叠度 | 差距 |
| --- | --- | --- | --- |
| Windows 内置方法 | 系统能力 | 100% | 5 步流程、无批量、无脚本化 —— 本产品要替代的对象 |
| TileIconifier | 开源工具（MIT） | ~20% | 定位磁贴美化；2017 年停更；Win11 兼容性存疑 |
| 网络 PowerShell 脚本 | 代码片段 | ~60% | 取巧实现（explorer 中转）、无 GUI、需自行拼装 |
| 系统优化工具合集 | 商业软件 | < 10% | 不覆盖 UWP 快捷方式场景 |

### 3.4 核心体验流程（1/5）

**主流程（Happy Path）**

```
[双击 AppShortcutCreator.exe]
        │ 约 0.3s（本机 212 项实测）
        ▼
[主窗口：应用列表已加载完毕]
        │ 输入关键词「计算器」
        ▼
[列表实时过滤，仅剩匹配项]
        │ 双击该行（或勾选后点「创建到桌面」）
        ▼
[创建快捷方式 → 写入桌面]
        │ < 0.1s
        ▼
[状态栏：「[成功] 计算器 → C:\Users\xxx\Desktop\计算器.lnk（创建成功）」]
        │
        ▼
[桌面出现图标 · 流程结束]
```

**分支流程**

| 编号 | 触发条件 | 系统行为 | 用户感知 |
| --- | --- | --- | --- |
| B1 | 关键词无匹配 | 列表清空 | 显示「未找到匹配的应用」占位提示 |
| B2 | 桌面已存在同名 .lnk | 删除旧文件后重建 | 状态栏提示「已存在，已覆盖」 |
| B3 | 单次创建失败（PIDL 解析失败 / 无权限） | 跳过该项，继续处理其余项 | 状态栏给出失败原因，不中断批量 |
| B4 | 特殊项（路径为空 / 协议链接） | 创建时跳过 | 提示「该项暂不支持创建」 |
| B5 | 批量中部分失败 | 继续执行剩余项 | 汇总「成功 N 个，失败 M 个」 |

**关键体验约束**

| 约束 | 指标 |
| --- | --- |
| 枚举必须在 1 秒内完成 | 本机 212 项基准 0.3s；期间显示加载态，不白屏 |
| 搜索逐字符即时响应 | 单次过滤 < 50ms，无需回车 |
| 创建不阻塞 UI | 单次 < 100ms；批量时窗口保持可响应，结果逐条追加 |
| 失败必须给中文可理解原因 | 禁止直接抛异常堆栈 |

### 4.3 涉及的页面结构（4/5）

产品为**单窗口应用**，无页面跳转、无弹窗表单（创建结果在状态栏就地反馈）。窗口固定 **720×520**（设计稿基准尺寸，按系统 DPI 等比放大），圆角 14px，标题栏自绘。窗口按六区布局：

### 5.2 非页面端功能逻辑设计

#### 5.2.1 应用枚举逻辑（M1）

```
输入：无
输出：List<AppEntry>{ Name, Kind(UWP|Win32|Unsupported), PathOrAumid }

1. 创建 Shell.Application COM 实例
2. folder = shell.Namespace("shell:AppsFolder")
3. 遍历 folder.Items()：
     name  = item.Name
     path  = item.Path            // UWP → AUMID；Win32 → exe 全路径；特殊项可能为空
     若 name 为空 → 跳过（分隔符等无效项）
     若 path 为空 → Kind = Unsupported
     否则若 File.Exists(path) 且扩展名为 .exe → Kind = Win32
     否则 → Kind = UWP
4. 按名称排序后返回
```

**约束**

- 枚举失败（COM 不可用）→ 返回空列表并抛出可捕获异常，由 GUI 转「错误态」
- 不修改、不缓存、不写入任何 Shell 状态（只读）
- 枚举期间不创建任何临时文件

#### 5.2.2 UWP 快捷方式创建逻辑（M2·核心）

```
输入：AUMID、应用名
输出：.lnk 文件

1. 解析 PIDL：
     hr = SHParseDisplayName("shell:AppsFolder\" + AUMID, IntPtr.Zero, out pidl, 0, out attrs)
     若 hr != S_OK 或 pidl == 0 → 失败（原因：无法解析应用标识）
2. 创建 IShellLinkW 实例（CLSID_ShellLink）
3. link.SetIDList(pidl)            // 关键：不是 SetPath
4. link.SetDescription(应用名)
5. persist = (IPersistFile)link
6. persist.Save(目标路径, true)     // remember = true
7. 释放 PIDL（ILFree）与 COM 对象（Marshal.ReleaseComObject）
```

> 采用 `SetIDList` 而非 `explorer.exe shell:AppsFolder\AUMID` 的取巧方案，保证产物与系统手动创建**完全同构**：图标自动继承、双击原生启动、随应用更新持续有效。

#### 5.2.3 Win32 快捷方式创建逻辑（M2）

```
输入：exe 全路径、应用名
输出：.lnk 文件

1. 创建 IShellLinkW 实例
2. link.SetPath(exePath)
3. link.SetWorkingDirectory(Path.GetDirectoryName(exePath))
4. link.SetIconLocation(exePath, 0)
5. link.SetDescription(应用名)
6. persist.Save(目标路径, true)
7. 释放 COM 对象
```

**Win32 路径旁注**：部分 Shell 条目返回的是 `{GUID}\xxx.exe` 形式的已知文件夹相对路径（如 `{1AC14E77-…}\cmd.exe` 指向 System32）。此类路径由 Shell 直接接受，无需展开，保持与开始菜单条目一致的表示。

#### 5.2.4 目标路径与命名规则（M5）

| 规则 | 实现 |
| --- | --- |
| 桌面定位 | `Environment.GetFolderPath(SpecialFolder.DesktopDirectory)`（兼容 OneDrive 重定向桌面） |
| 文件名 | `{清洗后的应用名}.lnk` |
| 清洗规则 | 逐字符剔除 `Path.GetInvalidFileNameChars()`（`\ / : * ? " < > \|` 等）；连续空白压缩为单个空格；去除首尾空格与句点 |
| 空名兜底 | 清洗后为空 → 使用 `快捷方式_{序号}` |
| 覆盖策略 | 目标已存在 → 先 `File.Delete` 再 `Save`；删除失败则直接覆盖写入 |
| 编码 | 文件名与 .lnk 内部描述统一 UTF-16（Windows 原生），文件名按系统区域设置正确落盘 |

#### 5.2.5 CLI 逻辑设计（M4）

| 参数 | 行为 | 输出 | 退出码 |
| --- | --- | --- | --- |
| 无参数 | 启动 GUI | — | 0（正常退出） |
| `--list` | 枚举并打印全部应用 | `序号\|名称\|类型\|路径或AUMID`，末行 `# 共 N 个应用(...)` | 0 |
| `--create <名称>` | 模糊匹配（不区分大小写）首个命中并创建 | 成功：`[成功] {名称} -> {路径}(创建成功\|已存在,已覆盖)`<br>失败：`[失败] ...` 或 `未找到名称包含…的应用` | 成功 0 / 失败 1 |
| `--create`（缺名称） | 打印用法 | `用法: --create <应用名称>` | 1 |
| 未知参数 | 打印用法提示 | 参数说明 | 1 |

**控制台附着策略**

- 程序 target 为 `winexe`（无控制台子系统），Main 入口首先尝试 `AttachConsole(ATTACH_PARENT_PROCESS)`
- 附着成功后重新绑定 `Console.Out` 到 `CONOUT$`，确保管道/重定向（`>`、`|`）下输出可用
- 无父控制台（双击启动）时跳过附着，不影响 GUI 模式
- 退出前 `FreeConsole` 并刷新 stdout，避免输出丢失

#### 5.2.6 错误码与用户文案映射（M5）

| 内部错误 | 用户可见文案 | 处理策略 |
| --- | --- | --- |
| `E_PARSE_AUMID` | 无法解析该应用的标识，暂不支持创建 | 跳过，继续下一项 |
| `E_NO_PATH` | 系统未提供该应用的路径信息，暂不支持创建 | 跳过 |
| `E_ACCESS_DENIED` | 无权限写入桌面，请以管理员身份运行 | 中止当前项 |
| `E_FILE_LOCKED` | 快捷方式正被占用，请关闭后重试 | 中止当前项 |
| `E_COM_INIT` | 系统组件初始化失败，请重启程序 | 全局错误 |
| `E_ENUM_FAIL` | 读取应用列表失败 | 保留旧列表，允许重试 |

**日志策略（v1.0）**

- 仅内存态：状态栏与结果汇总，不落盘
- 不做联网上报、不收集设备信息
- 崩溃信息依赖用户手动反馈 Issue（附 Windows 版本与应用版本）

#### 5.2.7 构建与版本逻辑（M6）
